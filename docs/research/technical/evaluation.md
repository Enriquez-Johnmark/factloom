# Evaluation of memory systems

Accessed: 2026-11-13.

## Question

Which public benchmarks exist for LLM memory systems, do they cover what Factloom is built for (facts
that change over time, contradictions, "what was true on date X"), what are their sizes, licences and
known weaknesses, and how can a one-person project build a small, deterministic evaluation set of its
own?

## Findings

### Benchmark overview

| Benchmark | Source | Size | Temporal questions | Knowledge-update / contradiction | Licence |
|---|---|---|---|---|---|
| LoCoMo | Maharana, Lee, Tulyakov, Bansal, Barbieri, Fang, 2024, https://arxiv.org/abs/2402.17753 | Public release: 10 conversations, 1,986 QA items | Yes (a temporal reasoning category) | No dedicated category | CC BY-NC 4.0 |
| LongMemEval | Wu, Wang, Yu, Zhang, Chang, Yu, ICLR 2025, https://arxiv.org/abs/2410.10813 | 500 questions; histories of about 115k tokens (S) or about 500 sessions (M) | Yes (`temporal-reasoning`) | Yes (`knowledge-update`) | MIT |
| DMR | Packer et al. (MemGPT), 2023, https://arxiv.org/abs/2310.08560 | 500 conversations, 5 sessions each | No | No | Unverified |
| MemoryAgentBench | Hu, Wang, McAuley, 2025, https://arxiv.org/abs/2507.05257 | Several datasets; counts not verified | Not verified | Yes ("selective forgetting" / "conflict resolution") | MIT |
| TimeQA | Chen, Wang, Wang, NeurIPS 2021 datasets track, https://arxiv.org/abs/2108.06314 | 20K questions over 5,060 time-evolving facts, easy and hard versions | Yes (its whole purpose) | Facts change over time in the source documents | BSD 3-Clause |
| CronQuestions | Saxena, Chakrabarti, Talukdar, ACL 2021, https://arxiv.org/abs/2106.01515 | "largest known Temporal KGQA dataset" (exact count not verified) | Yes, over a ready-made temporal KG | No | Unverified |
| VibeMemBench | Fan, Shi, Li et al., 2026, https://arxiv.org/abs/2609.23570 | 111 coding targets from 90 repositories; 3,634 history trajectories | No | No | Unverified |

Details and labels follow.

1. **LoCoMo.** The paper describes conversations of about "300 turns and 9K tokens on avg., over up
   to 35 sessions" and five question types: single-hop, multi-hop, temporal reasoning, open-domain
   knowledge and adversarial. **Confirmed** (paper). The public repository states that "the benchmark
   consists of ten conversations" and that this "is a subset of the conversations released
   previously ... The initial release contained 50 conversations"
   (https://github.com/snap-research/locomo, README). **Confirmed.** Counting `data/locomo10.json`
   on 2026-11-13 gave 10 conversations and 1,986 QA items in five numbered categories (282, 321, 96,
   841, 446). **Confirmed** by running a count; the mapping from category number to name was not
   verified. The repository licence file is Creative Commons Attribution-NonCommercial 4.0.
   **Confirmed.** The conversations are generated by LLM agents and then edited by human annotators.
   **Confirmed** (paper).

2. **LongMemEval covers both knowledge updates and temporal reasoning.** It tests "five core
   long-term memory abilities: information extraction, multi-session reasoning, temporal reasoning,
   knowledge updates, and abstention" with "500 manually created questions". Knowledge updates are
   defined as the "ability to recognize the changes in the user's personal information and update the
   knowledge of the user dynamically over time". **Confirmed** (paper). The dataset field
   `question_type` takes the values `single-session-user`, `single-session-assistant`,
   `single-session-preference`, `temporal-reasoning`, `knowledge-update` and `multi-session`;
   abstention questions are marked by an `_abs` suffix on the question id. `longmemeval_s` is about
   115k tokens (about 40 sessions) per question, `longmemeval_m` about 500 sessions, and
   `longmemeval_oracle` contains only the evidence sessions. A cleaned version was published in
   September 2025. Source: https://github.com/xiaowu0162/LongMemEval (README, LICENSE: MIT);
   https://huggingface.co/datasets/xiaowu0162/longmemeval-cleaned (card licence: mit).
   **Confirmed.**

3. **LongMemEval scores answers with an LLM judge and also supports retrieval metrics.** Answers are
   graded by a prompted `gpt-4o-2024-08-06`, for which the authors report "more than 97% agreement
   with human" experts; because answer locations are annotated, "we report Recall@k and NDCG@k" for
   retrieval. **Confirmed** (paper).

4. **DMR is small enough to fit in a context window.** The Deep Memory Retrieval task comes from the
   MemGPT paper and uses a 500-conversation subset of the Multi-Session Chat dataset. The Zep paper,
   which reports results on it, cautions that "each conversation contains only 60 messages, easily
   fitting within current LLM context windows" and reports full-conversation baselines close to the
   memory systems' scores (https://arxiv.org/abs/2501.13956). **Confirmed.** Licence of the
   underlying data: **unverified**.

5. **MemoryAgentBench tests handling of contradictory evidence directly.** Four competencies:
   accurate retrieval, test-time learning, long-range understanding, and selective forgetting ("the
   skill to revise, overwrite, or remove previously stored information when faced with contradictory
   evidence"). The repository README names the fourth "Conflict Resolution", lists a newly built
   `FactConsolidation` dataset, and scores it by `substring_exact_match` rather than an LLM judge.
   Reported result: "all methods fail on the multi-hop situation (with achieving at most 28%
   accuracy)". Sources: the paper; https://github.com/HUST-AI-HYZ/MemoryAgentBench (README, LICENSE:
   MIT); https://huggingface.co/datasets/ai-hyz/MemoryAgentBench (card licence: mit). **Confirmed.**
   The authors note the task "may appear specialized or even synthetic". **Confirmed.**

6. **TimeQA and temporal KGQA sets test reasoning, not memory maintenance.** TimeQA mines
   time-evolving facts from WikiData, aligns them with Wikipedia text, and generates 20K questions in
   easy and hard versions; the best model in the paper reached 46% against 87% human accuracy. Data
   and code are "issued under BSD 3-Clause" (https://github.com/wenhuchen/Time-Sensitive-QA).
   **Confirmed.** CronQuestions is question answering over an existing temporal KG. **Confirmed**
   (abstract). Fatemi et al., "Test of Time: A Benchmark for Evaluating LLMs on Temporal Reasoning"
   (2024, https://arxiv.org/abs/2406.09170) uses synthetic data because real-world facts "LLMs may
   have encountered during pre-training". **Confirmed** (abstract). None of these involve ingesting
   text incrementally and revising stored facts. **Confirmed** from the task descriptions.

7. **Benchmarks for coding-agent memory are recent.** VibeMemBench (arXiv, September 2026) evaluates
   memory systems on repository tasks where "executable tests decide task resolution", and argues that
   "memory benchmarks score recall without measuring downstream coding outcomes". **Confirmed**
   (abstract only; the paper body, data availability and licence were not checked). MemoryArena (He,
   Wang, Zhi et al., 2026, https://arxiv.org/abs/2602.16313) is not coding-specific but reports that
   "agents with near-saturated performance on existing long-context memory benchmarks like LoCoMo
   perform poorly in our agentic setting". **Confirmed** (abstract). A web search also surfaced other
   candidates (LongMemCode, CAPA, AMB) that were not verified against primary sources:
   **unverified**.

### Documented criticisms and disputes

8. **Zep's criticism of LoCoMo.** In the blog post "Is Mem0 Really SOTA in Agent Memory?"
   (https://blog.getzep.com/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/)
   Zep states that LoCoMo conversations (16,000 to 26,000 tokens by its count) fit in a context
   window; that the benchmark "lacks questions designed to test knowledge updates"; that "Category 5
   was unusable due to missing ground truth answers"; and that some questions have speaker
   attribution errors or are underspecified. It also states that the Mem0 paper's evaluation of Zep
   misused Zep's API, and reports 75.14% for Zep against 65.99% in the Mem0 paper. The post carries a
   correction notice saying an earlier version miscalculated Zep's score. **Confirmed** that the post
   says this; the claims themselves are a vendor's and were not independently checked. The page
   also carries a later banner: "We've published new LoCoMo scores for Zep: 80% at <200ms
   latency" (page fetched 2026-11-13; the banner's date is rendered as "December 9, 2015", which
   is presumably a typo for 2025). **Confirmed** that the banner says this.

9. **Mem0's side.** The Mem0 paper reports its own systems at 66.88% and 68.44% (LLM-judge score) on
   LoCoMo and a 26% relative improvement over OpenAI's memory
   (https://arxiv.org/abs/2504.19413). **Confirmed.** Secondary sources say Mem0 replied in
   `getzep/zep-papers` issue 5 that Zep's first figure wrongly included the adversarial category and
   that Zep's corrected score should be 58.44%. The issue could not be opened in this session.
   **Likely** (secondary sources only).

10. **Letta's filesystem result.** Letta reports that an agent with only file tools (`grep`,
    `search_files`, `open`, `close`) over the raw conversation file "achieves 74.0% on LoCoMo with
    GPT-4o mini", above Mem0's reported graph variant, and concludes that "current memory benchmarks
    may not be very meaningful". Source: https://www.letta.com/blog/benchmarking-ai-agent-memory
    (dated 12 August 2025). **Confirmed** that the post says this; vendor-reported.

11. **At least four different numbers are reported for the same system on the same benchmark**
    (65.99% in the Mem0 paper, 75.14% and later 80% from Zep, and reportedly 58.44% from Mem0's
    reply, all for Zep on LoCoMo). **Confirmed** for the first three, **likely** for the fourth. Whatever the cause, cross-vendor LoCoMo numbers are not a reliable
    basis for design decisions.

12. **MemoryAgentBench's authors criticise both conversational benchmarks**: "LOCOMO still features
    relatively short conversations (9k), and LongMemEval uses synthetic conversations with limited
    topical diversity". **Confirmed** (paper).

13. **Zep's own LongMemEval results show a regression on one category.** Against a full-context
    baseline, Zep reports lower accuracy on `single-session-assistant` questions (gpt-4o: 80.4%
    versus 94.6%) while improving on temporal reasoning (62.4% versus 45.1%). **Confirmed**
    (arXiv:2501.13956, results table). A memory layer can lose information that the raw text had.

### Metrics in use

| Metric | Used by | Notes | Label |
|---|---|---|---|
| Answer accuracy by LLM judge | LongMemEval, Mem0 (J score), Zep | Flexible but non-deterministic and model-dependent; LongMemEval reports >97% agreement with humans for its judge | Confirmed |
| Token-overlap F1, BLEU-1 | LoCoMo, Mem0 paper | Mem0 calls the LLM judge "complementary" to these | Confirmed |
| Exact or substring match | MemoryAgentBench conflict tasks | Deterministic; needs short canonical answers | Confirmed |
| Retrieval Recall@k, NDCG@k | LongMemEval | Needs gold evidence ids; isolates retrieval from generation | Confirmed |
| Executable tests | VibeMemBench | Measures task outcome, not recall | Confirmed (abstract) |
| Latency, context tokens | Zep, Mem0 | Reported alongside accuracy | Confirmed |
| Staleness or contradiction rate of the store itself | None found | No reviewed benchmark inspects stored state | Confirmed absence |

## What it means for Factloom

No public benchmark tests what is specific to Factloom: bi-temporal queries ("as known at T"),
supersession links, or the correctness of the stored state as opposed to a final chat answer. All of
them are conversational, and the largest directly relevant slice (LongMemEval knowledge-update plus
temporal-reasoning) is a fraction of 500 questions about personal chat. So: build a small internal
set first, and use public sets later as a sanity check, not as the target.

A cheap, deterministic internal evaluation in three layers. Layer A needs no LLM and is what
phase 1 can use; layers B and C need the LLM pipeline, which arrives in phase 2. The sizes are
starting suggestions; an independent review suggested starting B with about 10 scenarios (see
`../OPEN-QUESTIONS.md`, section C).

| Layer | What it checks | Needs an LLM at test time? | Size to start |
|---|---|---|---|
| A. Store semantics | Given fact rows inserted directly, are "now", "on date X", "as known at T" and supersession answers correct? | No | About 30 Vitest cases |
| B. Timeline scenarios | Given a scripted sequence of dated inputs, does the pipeline end with the right live facts, the right invalidations and the right links? | Recorded responses | 30 to 50 scenarios |
| C. Extraction cases | Given one input text, are the expected facts (subject, predicate, object, dates) extracted, and nothing forbidden? | Recorded responses | 50 to 100 inputs |

How to build it cheaply:

1. **Scenario format.** One YAML or JSON file per scenario: a list of steps
   `{ at: <timestamp>, text: <input> }`, then assertions
   `{ ask: { subject, predicate, validAt?, knownAt? }, expect: [objects], mustNotReturn: [objects] }`.
   Assertions query the store through the same API the MCP server uses; no natural-language answer
   and no judge are involved, so scoring is exact match on normalised values.
2. **Cover the outcome table from contradiction-detection.md deliberately**: duplicate, refinement,
   succession, correction, unrelated, late-arriving older fact, multi-valued predicate (must not
   invalidate), same name but different entity (must not merge), relative dates ("last week"),
   future statements ("will migrate in March").
3. **Source the texts from the first use case.** Write them in the style of coding-agent notes,
   commit messages and decisions ("switched the test runner from Jest to Vitest"). Drafting with an
   LLM is fine; every expected value is reviewed by hand. Do not copy LoCoMo text (non-commercial
   licence); LongMemEval and MemoryAgentBench are MIT-licensed if examples are ever adapted.
4. **Determinism through record and replay.** The LLM client interface (already a settled decision)
   gets a recording wrapper: the first run stores each request hash and response under `fixtures/`;
   CI replays them and fails on a missing fixture. A prompt or model change invalidates the hash,
   which forces an explicit re-record and makes the diff in results reviewable. Use a fixed injected
   clock so `created_at` values are stable.
5. **Separate "pipeline given these model outputs" from "model quality".** Replayed runs test the
   former on every commit. A manual, occasional live run against the real API measures the latter and
   reports variance over a few repetitions.

Metrics to compute from layers B and C (all deterministic):

| Metric | Definition |
|---|---|
| Current-fact accuracy | Share of "now" assertions whose expected objects are all returned |
| Staleness rate | Share of "now" assertions that return a `mustNotReturn` (superseded) object |
| Historical accuracy | Same as current-fact accuracy for `validAt` and `knownAt` assertions |
| False invalidation rate | Share of facts expected live that were invalidated |
| Missed invalidation rate | Share of facts expected invalidated that are still live |
| Extraction precision / recall | Against expected (subject, predicate, object) triples after normalisation |
| Over-merge / under-merge count | Entity pairs wrongly merged / wrongly kept apart |
| Retrieval Recall@k | Share of queries whose gold fact ids appear in the top k (layer B queries with free-text questions) |

Public benchmarks, later and in this order: (1) the knowledge-update and temporal-reasoning subsets
of LongMemEval `oracle` or `S`, reported per question type; (2) MemoryAgentBench's conflict tasks;
(3) a coding-memory benchmark such as VibeMemBench once its data and licence are confirmed. Report
alongside a full-context baseline, as the Zep paper does, since a memory layer can be worse than no
memory layer (finding 13).

Do not build yet:

- An LLM-judge harness. Layer A to C assertions avoid it; it is only needed for public QA benchmarks.
- A LoCoMo run. It lacks knowledge-update questions, is licensed non-commercial, and its published
  numbers are disputed (findings 8 to 11).
- A leaderboard comparison against other memory products. Comparing systems fairly is hard enough
  that the vendors themselves disagree on each other's scores.
- Large synthetic datasets. Fifty reviewed scenarios find more bugs than five thousand unreviewed.
- Latency benchmarking beyond a simple timing log per pipeline stage.
